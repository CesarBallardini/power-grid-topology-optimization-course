    1. Which device. python -c "import jax; print(jax.devices())" printed [CpuDevice(id=0)] in both environments, and environment_check.py reports backend cpu, kind CPU, x64 False (ToOp switches jax_enable_x64 on itself, see case57_toop.py).       environment_check.py
      """Which device JAX uses, and how much of a first run is compilation (Chapter 0).

Run it in any environment that has JAX (the course environment, the ToOp container or the course JupyterHub)::

    python environment_check.py

It prints the JAX version and device list, says whether the work goes to a GPU or to the CPU, and times a small
jitted computation twice: the first call includes XLA compilation, the second one only runs the compiled code.
"""

import time
from functools import partial
from typing import TYPE_CHECKING

import jax
import jax.numpy as jnp

if TYPE_CHECKING:
    from collections.abc import Callable, Sequence

GPU_PLATFORMS = ('gpu', 'cuda', 'rocm')


def device_kind(devices: Sequence) -> str:
    """``'GPU'`` if any device's ``platform`` is a GPU backend, else ``'CPU'``.

    ``jax.devices()`` returns ``[CudaDevice(id=0)]`` on a working GPU setup and ``[CpuDevice(id=0)]`` otherwise;
    the platform attribute is what the banner of the ToOp container tests as well.
    """
    return 'GPU' if any(getattr(d, 'platform', '').lower() in GPU_PLATFORMS for d in devices) else 'CPU'


def report() -> dict[str, str]:
    """Version, default backend, device list and kind of device, as strings ready to paste into lab notes."""
    devices = jax.devices()
    return {
        'jax': jax.__version__,
        'backend': jax.default_backend(),
        'devices': repr(devices),
        'kind': device_kind(devices),
        'x64': str(jax.config.read('jax_enable_x64')),
    }


def time_twice(fn: Callable, *args) -> tuple[float, float]:
    """Wall-clock seconds of two consecutive calls of ``fn(*args)``, blocking until the result is ready.

    For a jitted function the first call compiles (XLA) and runs; the second one only runs. Their difference is the
    compilation cost that every fresh process (or restarted kernel) pays again.
    """
    out = []
    for _ in range(2):
        start = time.perf_counter()
        jax.block_until_ready(fn(*args))
        out.append(time.perf_counter() - start)
    return out[0], out[1]


@partial(jax.jit, static_argnums=0)
def solve_laplacian(n_nodes: int = 200):
    """Solve a small dense linear system, the kind of work the DC solver does, as a stand-in for a load flow."""
    a = jnp.eye(n_nodes) * 2.0 - jnp.eye(n_nodes, k=1) - jnp.eye(n_nodes, k=-1)
    return jnp.linalg.solve(a, jnp.ones(n_nodes))


def main() -> None:
    """Print the device report and the two timings."""
    for key, value in report().items():
        print(f'{key:8s} {value}')
    first, second = time_twice(solve_laplacian)
    print(f'first call  {first * 1e3:8.1f} ms  (compile + run)')
    print(f'second call {second * 1e3:8.1f} ms  (run only)')
    print(f'compilation share of the first call: {100 * (first - second) / first:.0f} %')


if __name__ == '__main__':
    main()

    2. Two runs, two timings. The notebook was not run as a notebook here; case57_toop.py runs the same calls (case57_data_powsybl, load_grid, run_initial_loadflow) as a script. Two runs of the script in two fresh processes took 15.0 s and 14.3 s of wall-clock time, a 5 % difference, and a third fresh run 16.7 s: the second run is not reliably faster. The reason is that a restarted kernel (or a new process) compiles again: JAX keeps compiled programs in memory, and a persistent compilation cache on disk is off unless jax_compilation_cache_dir is set. What the second run saves is only what the operating system cached (imported modules, the data files), a few hundred milliseconds. Compilation shows up within one session: inside the script, the first run_initial_loadflow took 0.67 s and the second 0.50 s (0.81 s and 0.54 s on another run); in environment_check.py, the first call of a small jitted solve took 237 ms and the second 0.4 ms, so there the compilation is practically the whole first call. On a GPU the first call of a session also pays for the CUDA context, which is why the chapter asks to time twice without restarting in between. The notebook's "run all, restart, run all" therefore measures mostly disk caching, and the honest answer to "which part is compilation" is: almost none of the difference between the two notebook runs; the compilation is paid in both.

    3. The processed grid folder. Written into a new folder, the generator case57_data_powsybl(folder) leaves the output of the import stage: grid.xiidm (the grid model in pypowsybl format), masks/ (which lines, transformers, generators and substations the optimizer may touch), initial_topology/ (the substations as busbars and couplers, read later by the AC stage), loadflow_parameters.json (the settings for the AC load flow) and logs/. After load_grid, the DC preprocessing has added static_information.hdf5 (the arrays the GPU solver reads), static_information_stats.json, action_set.json and action_set_diffs.hdf5 (every busbar split the optimizer may try, and the same actions as changes of the incidence) and nminus1_definition.json (the contingency list, reused by the AC validation). Nothing in the folder belongs to the AC validation stage yet: its results go to a snapshot folder (optimizer_snapshots/) once an optimization has run. case57_toop.py prints this listing before and after load_grid and the stage of each entry; STAGE_OF in the script is the table.

      case57_toop.py
      """The first run of the pipeline as a script: what ``notebooks/example1_dc_loadflow_example.ipynb`` does (Chapter 0).

Run it inside the ToOp container (or with ToOp's virtual environment) from this folder::

    python case57_toop.py /tmp/case57

It writes the already imported IEEE 57 folder with ToOp's own generator, lists the files it contains before and
after the DC preprocessing, prints the node and branch counts of Exercise 5, and times the DC load flow twice to
separate compilation from execution (Lab step 2).
"""

import sys
import time
from pathlib import Path

import jax
import numpy as np
from fsspec.implementations.dirfs import DirFileSystem
from toop_engine_dc_solver.example_grids import case57_data_powsybl
from toop_engine_dc_solver.preprocess.convert_to_jax import load_grid, run_initial_loadflow
from toop_engine_interfaces.messages.preprocess.preprocess_commands import PreprocessParameters

jax.config.update('jax_enable_x64', True)

# Which stage of the pipeline writes each file of a processed grid folder (Lab step 3).
STAGE_OF = {
    'grid.xiidm': 'import (the grid model, pypowsybl format)',
    'loadflow_parameters.json': 'import (load-flow settings for the AC validation)',
    'masks': 'import (which lines, transformers, generators and substations the optimizer may use)',
    'initial_topology': 'import (the substations as busbars and couplers, for the AC stage)',
    'logs': 'import (start time of the run)',
    'static_information.hdf5': 'DC preprocessing (the arrays the GPU solver reads)',
    'static_information_stats.json': 'DC preprocessing (import statistics)',
    'action_set.json': 'DC preprocessing (every busbar split the optimizer may try)',
    'action_set_diffs.hdf5': 'DC preprocessing (the same actions as incidence changes)',
    'nminus1_definition.json': 'DC preprocessing (the contingency list, reused by the AC stage)',
}


def write_folder(folder: Path) -> list[str]:
    """Write the imported IEEE 57 folder with ToOp's generator into a new folder; return its entries, sorted."""
    if folder.exists() and any(folder.iterdir()):
        msg = f'{folder} is not empty: give a new folder, so that the listing shows what each stage writes'
        raise FileExistsError(msg)
    folder.mkdir(parents=True, exist_ok=True)
    case57_data_powsybl(folder)
    return entries(folder)


def entries(folder: Path) -> list[str]:
    """Top-level files and folders of a processed grid folder, sorted by name."""
    return sorted(p.name for p in folder.iterdir())


def load(folder: Path):
    """Preprocess the folder as the notebook does; return the static information and the network data."""
    _, si, network_data = load_grid(
        DirFileSystem(str(folder)),
        pandapower=False,
        parameters=PreprocessParameters(action_set_filter_bsdf_lodf=False, fail_on_non_convergence=False),
    )
    return si, network_data


def counts(si) -> dict[str, int]:
    """Node, branch and timestep counts of the preprocessed grid (Exercise 5)."""
    dyn = si.dynamic_information
    return {'n_nodes': int(dyn.n_nodes), 'n_branches': int(dyn.n_branches), 'n_timesteps': int(dyn.n_timesteps)}


def node_type_counts(network_data) -> dict[str, int]:
    """How many solver nodes of each type (``BUS``, ``BUS_B``, ``PSTNode``, ...): the answer to Exercise 5."""
    types, n = np.unique(np.asarray(network_data.node_types).astype(str), return_counts=True)
    return dict(zip(types.tolist(), n.tolist(), strict=True))


def branch_type_counts(network_data) -> dict[str, int]:
    """How many branches of each type (``LINE``, ``TWO_WINDINGS_TRANSFORMER``)."""
    types, n = np.unique(np.asarray(network_data.branch_types).astype(str), return_counts=True)
    return dict(zip(types.tolist(), n.tolist(), strict=True))


def timed_loadflows(si) -> tuple[float, float]:
    """Seconds of two consecutive ``run_initial_loadflow`` calls: the first compiles, the second only runs."""
    out = []
    for _ in range(2):
        start = time.perf_counter()
        si, metrics = run_initial_loadflow(si)
        jax.block_until_ready(si.dynamic_information.unsplit_flow)
        out.append(time.perf_counter() - start)
    return out[0], out[1]


def main(folder: Path) -> None:
    """Print the device, the files per stage, the counts and the two timings."""
    print('devices', jax.devices())
    before = write_folder(folder)
    print('after the import stage :', before)
    si, network_data = load(folder)
    after = entries(folder)
    print('after DC preprocessing :', after)
    for name in after:
        print(f'  {name:32s} {STAGE_OF.get(name, "?")}')
    print(counts(si))
    print('nodes by type   ', node_type_counts(network_data))
    print('branches by type', branch_type_counts(network_data))
    print('relevant substations', np.asarray(network_data.relevant_nodes).tolist())
    first, second = timed_loadflows(si)
    print(f'load flow: first {first:.3f} s, second {second:.3f} s')
    print('unsplit flow shape', tuple(si.dynamic_information.unsplit_flow.shape))


if __name__ == '__main__':
    main(Path(sys.argv[1]) if len(sys.argv) > 1 else Path('case57'))

    Exercise 1¶

    Electricity does not take the route an operator chooses: on a meshed grid it divides itself among all the parallel paths between where it is produced and where it is used, and the share of each path is set by the physics of the wires (a shorter, thicker wire takes more). When one line is overloaded, the operator can pay power plants to produce elsewhere, so that less power needs that corridor, which costs money. Or the operator can take one line out: the power that used that line now spreads over the remaining paths, and if the line removed was feeding into the overloaded corridor, the overloaded line ends up carrying less. Removing a wire can also make a different line worse, so the operator checks every line before and after. Chapter 16 turns "the physics of the wires" into a linear model where this effect is a single number per line pair, and Chapter 17 names it the LODF.

    Exercise 2¶

    Action What changes physically Cost to execute
    Line switching A circuit breaker opens (or closes) at both ends of a line; the line carries no current and the rest of the grid takes its flow No fuel or market payment; wear on the breaker and a lower security margin (one path fewer)
    Busbar splitting In a substation with two busbars, the coupler between them opens; the lines, generators and loads of that substation are now in two electrical nodes, each with the branches connected to its busbar No payment; a few switching operations, done remotely
    Busbar reassignment A branch's disconnectors move it from busbar A to busbar B (or back) while the coupler stays open or closed as decided; the branch joins the other node No payment; more switching operations than a plain split, and a short interruption of the branch if it cannot be transferred live
    PST tap change The tap changer of a phase-shifting transformer moves one or more steps, changing the phase angle the transformer adds; flow is pushed from one corridor to another No payment; mechanical wear of the tap changer, and the operating range is limited by the tap positions

    The point of the chapter: all four are non-costly in the sense of the market (no redispatch payment), which is why ToOp searches among them before an operator pays for redispatch. None is free of operational consequences (switching wear, protection settings, reduced margins), which is why the AC validation stage exists.

    Exercise 3¶

    With ToOp's environment, both JAX_PLATFORMS=cpu python -c "import jax; print(jax.devices())" and the same line without the variable printed [CpuDevice(id=0)] on this machine. The output shows that JAX will put every array and every computation on the CPU, whatever the hardware: JAX_PLATFORMS is a restriction of the backends JAX may use, not a request for one. On a machine where the toop-gpu service works, the same command without the variable prints [CudaDevice(id=0)]; with it, [CpuDevice(id=0)]. The variable therefore lets you run the same code and the same container image on both devices and compare: the wall-clock time of the solver (the second run of a session, see Lab step 2), and the results, which should agree to floating-point precision since ToOp forces float64 on both. It is also the first thing to check when a GPU container "runs slowly": a stray JAX_PLATFORMS=cpu in the environment is one of the silent failures the device banner names.

    Exercise 5¶

    n_nodes is 72 and n_branches is 82 (counts(si) in case57_toop.py; the notebook's own Markdown states the same two numbers). The hypothesis to form: the solver does not count buses, it counts electrical nodes, and a substation can be more than one node. The breakdown from node_type_counts and branch_type_counts:

    Type Count Where it comes from
    BUS 58 the 57 IEEE buses plus PSTBus, the extra bus that powsybl_extended_case57 adds to hang a phase-shifting transformer on
    PSTNode 1 the internal node of that PST, added at the stage combine_phaseshift_and_injection (n_nodes 58 to 59) so that the DC solver can control its angle
    REDUCED_NODE 1 a node the preprocessing adds while it handles bridges (the log shows n_nodes go from 59 to 60 at the stage exclude_bridges_from_outage_masks)
    BUS_B 12 one second busbar for each of the 12 substations that keep at least one split action (relevant substations [4, 7, 12, 16, 17, 19, 20, 21, 24, 33, 46, 50], zero-based node indices); the preprocessing log shows n_nodes jump from 60 to 72 at the stage add_bus_b_columns_to_ptdf

    So \(72 = 57 + 1 + 1 + 1 + 12\). The branches are the 80 of IEEE 57 (63 lines and 17 transformers) plus the two elements of the fake PST, PSTLine and PST: 64 lines and 18 two-winding transformers, \(82 = 80 + 2\). create_busbar_b_in_ieee in the generator gives every bus a busbar B and a coupler, but only the substations that can be split (four or more branches, Chapter 19, Exercise 8) become two solver nodes; the others collapse back into one. Chapter 13 explains the busbar model and Chapter 22 the preprocessing stages that produce these counts.
